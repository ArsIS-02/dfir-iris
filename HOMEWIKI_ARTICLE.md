# DFIR-IRIS — управление инцидентами ИБ

<h1 align="center">DFIR-IRIS</h1>

**Платформа регистрации и расследования инцидентов ИБ. Алерты Graylog попадают в очередь IRIS автоматически — остаётся триажить и эскалировать в кейсы.**

Адрес: **https://iris.apps.monitoring.test/** (плитка «DFIR-IRIS» в Atrium, группа Security)
Вход: **administrator / AdminHomelab2026** (пароль можно сменить: профиль → Change password)

![Дашборд IRIS](/static/articles/iris/dashboard.png)

---

## 1. Что это и зачем

DFIR-IRIS (LGPL-3.0, полностью open source) — система ведения расследований: очередь алертов, кейсы инцидентов, IOC, ассеты, задачи, заметки, таймлайн, доказательства с SHA-256, PDF-отчёты.

В нашей лаборатории цепочка такая:

```
Graylog High-алерт → TicketBridge → GLPI (тикет на работу)
                                 └→ IRIS (алерт на расследование)
```

GLPI отвечает за учёт работ, IRIS — за расследование инцидента. Ручной ввод не нужен: каждый High-алерт Graylog автоматически появляется в IRIS → Alerts.

## 2. Ежедневная работа: от алерта до закрытия инцидента

### Шаг 1. Очередь алертов
Меню слева → **Alerts**. Фильтр `is:open` показывает открытые алерты. В списке видны название, критичность (High/Medium/Low по приоритету Graylog), клиент, статус и время события.

В IRIS v3 доступны три представления: **List view** (список), **Split triage** (очередь и детали выбранного алерта) и **Board view** (доска по статусам). Вкладки **My queue**, **Unassigned**, **Escalated** и **All open** помогают сузить очередь; есть поиск, фильтры и сортировка.

![Очередь открытых алертов Graylog в IRIS v3](/static/articles/iris/alerts.png)

### Шаг 2. Триаж
Выбери строку алерта в очереди. В режиме **Split triage** справа откроются детали; на узком экране вместо списка откроется карточка алерта, а вернуться можно кнопкой **Back to queue**.

На вкладке **Overview** находятся описание, ссылка на источник, ответственный и история. В описании алертов лаборатории могут быть ссылки на разбор в HomeWiki, отчёт TrafficLens и блокировку IOC в BlockBoard. Вкладка **Raw event** показывает исходный JSON события Graylog; также доступны **Assets**, **Cluster**, **IOCs**, **Timeline**, **Notes**, **Comments** и **Graph**.

![Карточка алерта в IRIS v3: описание, источник и триаж](/static/articles/iris/alert-detail.png)

- Назначить ответственного → **Assign**.
- Изменить состояние → меню текущего статуса рядом с **Assign**.
- Настоящий инцидент → **Escalate to case**.
- Для быстрой работы в Split triage есть клавиши: `j`/`k` — навигация, `e` — эскалация, `x` — выбор, `m` — объединение.

### Шаг 3. Кейс (инцидент)
После эскалации открывается кейс. Заполняй по мере расследования:

![Кейс инцидента в IRIS v3: сводка и рабочие разделы](/static/articles/iris/case.png)
- **IOCs** — индикаторы (IP, домены, хэши). Можно обогащать через модули.
- **Assets** — затронутые хосты/учётки.
- **Notes** — ход расследования (что проверил, что нашёл).
- **Timeline** — хронология событий и действий.
- **Tasks** — чек-лист действий (шаги можно брать из runbook HomeWiki).
- **Evidence** — файлы-доказательства (дампы, скриншоты), хэшируются автоматически.
- **Datastore** — файлы кейса; панель открывается кнопкой **Toggle DataStore panel**.

### Шаг 4. Закрытие и отчёт
Когда инцидент решён, переведи кейс в **Closed** и заполни **Closing note**. Отчёт формируется через **Case menu**. Тикет в GLPI закроется автоматически при восстановлении хоста или по TTL (сутки тишины) — это делает TicketBridge.

## 3. Типовые сценарии

**IoC-алерт (TrafficLens/BlockBoard):** алерт в IRIS → в описании ссылка «Заблокировать» → блокировка в BlockBoard → в кейсе зафиксировать IOC, хост, время → закрыть после проверки.

**Агент молчит (HomeRepo):** алерт «устройство молчит больше суток» → проверить хост → при возвращении агента TicketBridge сам закроет тикет GLPI, в IRIS алерт закрой вручную.

**Расследование pcap:** алерт → ссылка на отчёт TrafficLens → граф соединений, файлы, сигнатуры → выводы в Notes кейса, IOC — в IOCs.

## 4. API (для своих интеграций)

Ключ: профиль (правый верхний угол) → **API Key** → Renew (после Renew старый ключ перестаёт работать!). В IRIS v3 используется endpoint `POST /api/v2/alerts`.

```bash
curl -sk -X POST 'https://iris.apps.monitoring.test/api/v2/alerts' \
  -H 'Authorization: Bearer <API_KEY>' -H 'Content-Type: application/json' \
  -d '{
    "alert_title": "Тестовый алерт",
    "alert_description": "Описание",
    "alert_source": "Graylog",
    "alert_source_ref": "test-001",
    "alert_severity_id": 5,
    "alert_status_id": 2,
    "alert_source_event_time": "2026-11-11T08:00:00",
    "alert_customer_id": 1,
    "alert_source_content": {}
  }'
```

Справочник severity: 6 Critical, 5 High, 1 Medium, 4 Low, 3 Informational. Статус 2 = New. Маппинг в TicketBridge: Graylog priority 3→High, 2→Medium, 1→Low. В конфигурации TicketBridge задано `TB_IRIS_API_PATH=/api/v2/alerts`.

## 5. Почтовые уведомления

**Исходящая почта IRIS настроена 11.11.2026.** Используется тот же ящик и пароль приложения, что в Graylog: `smtp.mail.ru:465`, Implicit SSL, аутентификация включена. Адрес отправителя — `arsentyev_is@mail.ru`, отображаемое имя — **IRIS Homelab**. Пароль не хранится в Git или `.env`. Штатный **Send test** и реальное фирменное уведомление успешно переданы SMTP; визуальное отображение во входящих проверяется отдельно.

IRIS v3 поддерживает два канала уведомлений: внутри приложения (**in_app**) и по электронной почте (**email**). Для исходящей почты используется **Settings → Server settings → OUTBOUND MAIL (SMTP)**. Там задаются сервер, порт, учётные данные, STARTTLS или Implicit SSL, адрес и имя отправителя. Кнопка **Send test** сохраняет конфигурацию и отправляет простое системное письмо, а не фирменный HTML-шаблон.

Адрес администратора заменён с `administrator@localhost` на рабочий ящик. В **My profile → Notifications** для него включена почта об упоминаниях, назначении задач и кейсов, изменении состояния кейса, назначении и эскалации алертов, сообщениях и ответах War Rooms. AI-предложения и пользовательские события модулей по почте отключены. Общие значения по умолчанию находятся в **Settings → Platform → Notifications**. Адрес дополнительно задан параметром `IRIS_ADM_EMAIL` в `docker-compose.v3.yml`: без него штатный `post_init` возвращает `administrator@localhost` после каждого перезапуска.

**Отдельного события `alert_created` в IRIS v3 нет.** Поэтому схема без дублирования такая:

- **Graylog** — мгновенное письмо о новом алерте;
- **IRIS** — письма о назначении/эскалации алертов, задачах, кейсах, упоминаниях и War Rooms.

### Как выглядит письмо IRIS Homelab

Для рабочих уведомлений действует фирменный тёмный HTML-шаблон в стиле писем Graylog. Цвет шапки показывает критичность: красный — High/Critical, оранжевый — Medium, синий — Low, зелёный — Informational. Названия событий и основные подписи переведены на русский. Одновременно сохраняется текстовая версия письма.

**Хост события выведен первым основным полем.** Он определяется по `group_by_fields`, полям события или источнику Graylog. Далее указаны критичность, статус, источник, ответственный, клиент и теги. **Время уведомления** — актуальный момент формирования письма; **время исходного события** показано отдельно, чтобы старый алерт не выглядел только что созданным. Даты указываются по Екатеринбургу с явным `UTC+05:00`.

HTML-описание TicketBridge преобразуется в чистый структурированный текст: никаких `<b>`, `<br>`, `<table>` и сплошной вёрстки в письме. Повторяющиеся заголовок, старая метка времени, числовой приоритет и ссылка HomeWiki убираются из описания — они уже есть в основных полях и кнопках. Технические поля Graylog (ID события и правила, окно проверки, поля события, MITRE ATT&CK при наличии) сохраняются. Длинные данные ограничиваются, а пароли, токены и ключи рекурсивно исключаются из рассылки.

**Индикаторы компрометации показываются отдельным блоком IOC.** Письмо собирает их из полей Graylog `ioc`/`ioc_type`, списков `iocs` и вкладки **IOCs** самого алерта IRIS (`alert.iocs`), удаляя дубликаты. Для IP-адресов и доменов создаются кнопки **«Заблокировать …»** в BlockBoard. Хэши отображаются в списке, но не получают неприменимую кнопку блокировки. Если Graylog передал `tl_report`, в письме сохраняется кнопка **«Отчёт TrafficLens»**.

Доступны кнопки:

- **Открыть в IRIS** — карточка алерта или другой объект уведомления;
- **Источник в Graylog** — Replay Search исходного события;
- **Разбор в HomeWiki** — рунбук соответствующего правила Graylog;
- **Заблокировать …** — подготовленная блокировка IP или домена в BlockBoard, действие подтверждается в интерфейсе;
- **Отчёт TrafficLens** — отчёт анализа, если его ссылка была в событии.

Если исходный объект уже удалён, IRIS отправит универсальное уведомление с сохранёнными заголовком и текстом. Небезопасные `javascript:`-ссылки и ссылки с учётными данными отклоняются, динамический текст экранируется.

11.11.2026 в 13:16 (UTC+5) выполнена повторная сквозная проверка на реальном алерте № 14: письмо с хостом, чистым описанием и актуальным временем прошло очередь Celery и было принято SMTP. Тестовая запись удалена, алерт не изменялся. В 13:42 (UTC+5) SMTP принял отдельное письмо **«ТЕСТ IoC»** с безопасными тестовыми значениями `203.0.113.66`, `evil.example`, хэшем EICAR, двумя ссылками BlockBoard и отчётом TrafficLens; база алертов не изменялась. Для проверки получения смотри входящие и спам рабочего ящика.

Файлы шаблона: `custom/mail/outbound.py` и `custom/templates/email/notification.html`. В `docker-compose.v3.yml` они подключены к app и worker через `:ro,z`; адрес для ссылок задаёт `IRIS_PUBLIC_URL=https://iris.apps.monitoring.test`. После правки шаблона перезапусти `iris3test_app` и `iris3test_worker`. Локальная проверка: `python -m unittest discover -s tests -v`.

Разделы **INBOUND MAIL (IMAP)** и **Alerts → Mail ingest / Mail rules** отвечают за обратную задачу — создание объектов IRIS из входящих писем. Для исходящих уведомлений их настраивать не нужно. Пароль SMTP хранится зашифрованным; после смены `SECRET_KEY` его необходимо ввести заново.

```bash
# Перезапуск / остановка / поднятие
systemctl --user restart dfir-iris     # осторожно: down+up всего стека

# Обновление версии: сначала бэкап и проверка на копии, затем
```

Особенности нашей установки (что чинили): SELinux — `chcon -R -t container_file_t ~/dfir-iris-v3-test/certificates/`; права на ключ nginx — 644; `IRIS_WORKER` в `.env` не задавать (иначе приложение падает с «A secret key is required to use CSRF»).
